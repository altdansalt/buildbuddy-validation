# QueryWriteStatus is unimplemented for unknown and finalized uploads

Title: QueryWriteStatus is unimplemented for unknown and finalized uploads
Components: app
Image version/digest: enterprise-v2.314.0; gcr.io/flame-public/buildbuddy-app-enterprise@sha256:ed321abe352bc7fa58101e979ff13fd153ccef98a3609e44aef4075848629843
Severity: medium
Severity justification: Clients cannot obtain the authoritative resume offset or confirm upload completion after a lost response. Restarting transfers wastes bandwidth; clients requiring the ByteStream resume contract cannot recover normally. Requires cache access; no cross-group data exposure is demonstrated.
Status: confirmed
Repro test target: //tests/app/bytestream:query_status_bug_test
BuildBuddy invocation: https://app.buildbuddy.io/invocation/ba690695-8ccb-40a3-9a9e-ce7cfce7b599

## Expected behavior

The [ByteStream contract](https://github.com/googleapis/googleapis/blob/master/google/bytestream/bytestream.proto)
requires `NOT_FOUND` for a nonexistent upload, and a `QueryWriteStatusResponse`
for an existing resource. After a successfully finalized uncompressed upload,
`complete` should be true and `committed_size` should equal the uploaded size.
The returned size is the offset clients use to resume an interrupted write;
retaining zero bytes of partial progress is allowed, but does not justify
returning `UNIMPLEMENTED` for completed resources.

## Actual behavior

Both querying a new upload name and querying that same name after successful
`Write(finish_write=true)` return `UNIMPLEMENTED: not implemented`. The test
checks the successful write's committed size and reads back identical bytes
before testing completed status, ruling out missing data and auth/config errors.

Both independent uncached runs reproduced the same result with fresh isolated
app containers, the harness default SQLite/Pebble configuration, self-auth, and
fixture-provisioned API keys. No image overrides or external services were used.
The passing regression suite verifies normal upload/readback, valid EOF reads,
invalid negative ranges, and interrupted-upload restart:
https://app.buildbuddy.io/invocation/db4b574f-7b68-499d-9679-46aaff49b411.
The RPC is made directly through the generated ByteStream client, not through a
proxy or the harness transfer helper.

Reproduction 1: https://app.buildbuddy.io/invocation/ba690695-8ccb-40a3-9a9e-ce7cfce7b599
Reproduction 2: https://app.buildbuddy.io/invocation/f791cc30-f14d-42a6-ab8f-a361e7ae59ba

The [released handler](https://github.com/buildbuddy-io/buildbuddy/blob/v2.314.0/server/remote_cache/byte_stream_server/byte_stream_server.go#L867)

## Verification

Verdict: **confirmed**. Both the unknown-name and completed-name subtests
returned `UNIMPLEMENTED` in both runs. The completed-name control first received
the correct Write committed size and read back identical data, so auth failure,
invalid naming, eviction, and unsuccessful finalization do not explain the result.

The [ByteStream QueryWriteStatus contract](https://github.com/googleapis/googleapis/blob/f5f34cc12374c1b3c11240e3d733b34ad0f63f49/google/bytestream/bytestream.proto#L76)
requires `NOT_FOUND` for a nonexistent resource; its response defines completion
and committed size. REAPI does not exempt this method. In the
[pinned handler](https://github.com/buildbuddy-io/buildbuddy/blob/v2.314.0/server/remote_cache/byte_stream_server/byte_stream_server.go#L867),
authenticated requests unconditionally return Unimplemented without checking the
resource. This is intentional implementation behavior: the comment references
[Bazel PR #28235](https://github.com/bazelbuild/bazel/pull/28235), which avoids
repeated queries after Unimplemented. That client fallback explains compatibility
with Bazel but does not amend the server contract or make the test incorrect.
The anonymous blackhole branch is inapplicable to the fixture's authenticated
client. Persisting partial progress is not required to fix these two cases.

Severity remains **medium** for loss of protocol-based recovery/completion checks
and redundant uploads. Bazel's fallback limits practical impact for tolerant
clients; no data loss, security boundary violation, or universal build failure
is established.

Reviewed independently from PR #37, commit
`bfa62ced1461a293568e6096d60fab99dc40339d`, against the digest-pinned
enterprise-v2.314.0 app above. Both uncached hosted runs started fresh isolated
app containers and logged that exact image reference. Requests used fixture-local
loopback endpoints and disposable authenticated group keys. No image/config
or environment overrides were passed. The two-minute RPC context did not expire.
The harness uses valid SHA256 resource names and random v4 upload UUIDs; the
bug assertions call the generated ByteStream client directly.

[REAPI CAS upload/download rules](https://github.com/bazelbuild/remote-apis/blob/6def1c5d27a527c400875c24ae8b1a160145d7e1/build/bazel/remote/execution/v2/remote_execution.proto#L213)
incorporate ByteStream and define the resource names used here. All reproducers
use uncompressed data, so compressed committed-size/offset exceptions do not
apply. The pinned release's
[enterprise cache documentation](https://github.com/buildbuddy-io/buildbuddy/blob/v2.314.0/docs/enterprise-cache-setup.md#use-pebble-on-persistent-ssd-storage)
recommends Pebble and documents inline storage of small artifacts; this fixture
is a supported single-app configuration, not a missing distributed-cache setup.
No documented protocol exception was found in the cache configuration/setup or
cache read/write architecture docs.
