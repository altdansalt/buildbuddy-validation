# ByteStream Read past EOF panics instead of returning OUT_OF_RANGE

Title: ByteStream Read past EOF panics instead of returning OUT_OF_RANGE
Components: app
Image version/digest: enterprise-v2.314.0; gcr.io/flame-public/buildbuddy-app-enterprise@sha256:ed321abe352bc7fa58101e979ff13fd153ccef98a3609e44aef4075848629843
Severity: medium
Severity justification: A cache-authorized client can trigger a recovered server panic with an ordinary malformed read offset. The RPC returns an unexpected internal error and generates a stack trace; no process exit or broader denial of service is established.
Status: confirmed
Repro test target: //tests/app/bytestream:read_past_end_bug_test
BuildBuddy invocation: https://app.buildbuddy.io/invocation/ba690695-8ccb-40a3-9a9e-ce7cfce7b599

## Expected behavior

The [ReadRequest contract](https://github.com/googleapis/googleapis/blob/master/google/bytestream/bytestream.proto)
says a `read_offset` greater than the size of the resource must return
`OUT_OF_RANGE`. For the 15-byte blob `offset boundary`, offset 16 must be rejected
without panicking.

## Actual behavior

After successfully writing the 15-byte blob, reading its valid resource name
with offset 16 returns `INTERNAL: A panic occurred`, rather than `OUT_OF_RANGE`.
The separate passing tests confirm that reading exactly at EOF succeeds and
negative offsets return `OUT_OF_RANGE`.

Both independent uncached runs reproduced the same result with fresh isolated
app containers, the harness default SQLite/Pebble configuration, self-auth, and
fixture-provisioned API keys. No image overrides or external services were used.
The passing regression suite verifies normal upload/readback, valid EOF reads,
invalid negative ranges, and interrupted-upload restart:
https://app.buildbuddy.io/invocation/db4b574f-7b68-499d-9679-46aaff49b411.
The RPC is made directly through the generated ByteStream client, not through a
proxy or the harness transfer helper.

Reproduction 1: https://app.buildbuddy.io/invocation/ba690695-8ccb-40a3-9a9e-ce7cfce7b599
Reproduction 2: https://app.buildbuddy.io/invocation/f791cc30-f14d-42a6-ab8f-a361e7ae59ba

## Logs excerpt

```text
offset past end: got rpc error: code = Internal desc = A panic occurred; want OutOfRange
```

## Notes

Run `GIT_CONFIG_GLOBAL=/dev/null bb remote test //tests/app/bytestream:read_past_end_bug_test --test_tag_filters=bug --nocache_test_results`.

The minimal payload is small enough to use uncompressed inline Pebble storage.
The [released Read handler](https://github.com/buildbuddy-io/buildbuddy/blob/v2.314.0/server/remote_cache/byte_stream_server/byte_stream_server.go#L107)
checks negative offsets but does not check the upper boundary before calling
the cache reader. Full logs and container inspect metadata are in each target's
undeclared outputs. Mitigation: validate offsets in clients; the server must
still handle invalid requests. No claim is made that the entire app crashes.
Independent verification is recorded below.

## Verification

Verdict: **confirmed**. Both runs returned `INTERNAL: A panic occurred` and
preserved the same server panic: `slice bounds out of range [16:15]` at
`enterprise/server/filestore/filestore.go:741`. The preceding successful upload
establishes an existing 15-byte resource; offset 16 is intentionally invalid.

The [ByteStream read_offset contract](https://github.com/googleapis/googleapis/blob/f5f34cc12374c1b3c11240e3d733b34ad0f63f49/google/bytestream/bytestream.proto#L99)
explicitly requires `OUT_OF_RANGE` beyond resource size. REAPI's uncompressed
read rules add no exception. The release's
[Read preconditions](https://github.com/buildbuddy-io/buildbuddy/blob/v2.314.0/server/remote_cache/byte_stream_server/byte_stream_server.go#L107)
validate only negative ranges, then pass the upper offset to Pebble. Its
[readerForMetadata](https://github.com/buildbuddy-io/buildbuddy/blob/v2.314.0/enterprise/server/backends/pebble_cache/pebble_cache.go#L3821)
passes this offset unchanged for uncompressed, unencrypted storage, and
[InlineReader](https://github.com/buildbuddy-io/buildbuddy/blob/v2.314.0/enterprise/server/filestore/filestore.go#L740)
slices `f.GetData()[offset:]` without a bounds check. The observed stack matches
this path. This is not a harness panic or an unsupported storage backend.
The passing range controls cover negative offsets and EOF on a larger blob;
they do not establish every boundary on this exact inline blob.

Severity remains **medium** for an authenticated input triggering a recovered
server panic and the wrong RPC status. The evidence establishes neither process
termination nor broader denial of service; backend-specific reproduction should
not be generalized to every blob size or cache backend.

is a supported single-app configuration, not a missing distributed-cache setup.
No documented protocol exception was found in the cache configuration/setup or
cache read/write architecture docs.
